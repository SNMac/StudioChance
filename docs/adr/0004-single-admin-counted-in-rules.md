# 점포 관리자 1명을 Rules에서 멤버 값의 모양으로 센다

점포마다 관리자는 정확히 한 명이다. 이 불변식을 Firestore Rules가 점포 생성·수정마다 검증한다. 스키마는 바꾸지 않는다. `memberById`의 값이 `{role: ...}` 하나뿐이라는 점을 이용해, 전체 멤버 수에서 `{'role': 'ADMIN'}`을 모두 지운 수를 빼면 관리자 수가 된다(`values().size() - values().removeAll([{'role': 'ADMIN'}]).size() == 1`). UseCase도 같은 규칙을 검증하지만 이는 더 나은 오류 메시지와 회원 탈퇴 전 판정을 위해서다. 보안 경계는 Rules다(D2).

관리자가 아닌 사람이 관리자가 되는 경로(가입 신청, 점포 나가기, 신청 취소)는 쓰는 키가 본인 uid로 정해져 있어 이 식이 없어도 Rules로 막을 수 있다. 이 식이 막는 것은 관리자 쪽 쓰기에서 생기는 위반이다. ADMIN으로 승인하기, 다른 멤버를 관리자로 올리기, 관리자 강등·본인 추방, 위임 도중 관리자가 0명이나 2명이 되는 경우가 여기에 해당한다. 관리자는 이미 점포를 삭제할 수 있으므로 공격이 아니라 **앱 버그를 서버에서 걸러내는 것**이 목적이다.

## 대가

이 식은 멤버 값이 정확히 `{role: ...}` 모양이라는 전제에 기댄다. `StoreMemberInfoModel`에 필드가 하나라도 늘면(예: `joinedAt`) 관리자가 `{'role': 'ADMIN'}`과 일치하지 않아 0명으로 세지고, 관리자의 모든 점포 수정이 거부된다. Rules 주석과 Rules 테스트로 이 전제를 고정한다. 필드를 늘려야 한다면 아래 `adminUid` 방식으로 옮긴다.

## Considered Options

- **UseCase에서만 검증**: Rules가 맵 값을 순회할 수 없다고 보고 처음에 고려했다. 관리자는 이미 모든 권한을 가지므로 보안상 문제는 없지만, 앱 버그로 관리자가 없는 점포가 생기는 것을 막지 못한다.
- **점포 문서에 `adminUid` 필드 추가**: `isAdmin()`이 이 필드를 기준으로 판정하도록 바뀌어 권한상 관리자는 구조적으로 한 명이 된다. 대신 스키마·생성 경로·Rules 판정 기준이 함께 바뀌고, `memberById`의 ADMIN 표기가 둘 이상 생기는 것은 여전히 막지 못한다. 출시 후에는 데이터 마이그레이션이 필요하다.
- **관리자 위임을 Callable Function으로 처리**: 서버에서 트랜잭션을 보장할 수 있지만 위임 한 경로만 지키고, 승인·역할 변경 경로의 위반은 그대로 남는다.
