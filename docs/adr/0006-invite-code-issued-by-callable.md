# 초대 코드 발급은 Callable이 서버 시각으로 한다

초대 코드는 관리자가 점포 문서에 직접 쓰지 않고 Callable `issueInviteCode`로 발급한다. 관리자는 Rules상 점포 문서의 다른 필드는 모두 쓸 수 있지만 `inviteInfo`는 `null`로만 쓸 수 있다. `null`은 점포 삭제 때 쓴다. 클라이언트가 발급 시각을 쓸 수 있으면, 관리자가 앱을 거치지 않고 미래 시각을 적어 15분인 유효 시간을 마음대로 늘릴 수 있다. 조회(`lookupInviteCode`, D11)는 이미 서버 시각으로 만료를 판정하므로, 발급도 서버로 옮겨 만료 판정과 발급 시각의 출처를 서버 하나로 맞춘다.

발급할 때 유효한 코드가 남아 있으면 서버는 그 코드를 그대로 돌려준다. 화면이 기기 시계로 만료라고 판단해 [발급]을 보여 줬더라도 서버 기준으로 살아 있는 코드라면, 새로 만들어 이미 공유한 코드를 관리자도 모르게 무효로 만들지 않기 위해서다. 새 코드는 다른 점포가 쓰는 코드와 겹치지 않게 고른다. 만료된 코드도 겹치는 것으로 본다. 조회가 코드가 같은 점포를 하나만 가져오기 때문이다.

남은 유효 시간 표시는 기기 시계에 Callable `getServerTime`으로 구한 서버와의 오차를 더해 계산한다. 오차는 초대 코드 화면을 열 때마다 새로 구하고, 응답 전이거나 실패하면 기기 시계를 그대로 쓴다. 표시는 판정이 아니므로 틀려도 안전하다. 다만 표시가 서버 판정과 어긋나면 관리자가 곧 만료될 코드를 공유하게 되므로 보정한다.

이전에는 앱이 `system/serverTime` 문서에 `serverTimestamp()`를 쓰고 바로 다시 읽어 서버 시각을 얻었다. 모든 사용자가 한 문서에 쓰므로 문서당 쓰기 속도 제한에 걸릴 수 있었고, 이 결정과 함께 그 문서와 규칙을 없앴다.

## Considered Options

- **Rules에서 `createdAt == request.time` 강제**: 미래 시각 주입은 막지만 재사용 판정이 클라이언트에 남아 `system/serverTime` 왕복이 계속 필요하다. 수정·생성·삭제(`null`) 경로마다 조건을 따로 걸어야 해 Rules도 복잡해진다.
- **서버 시각을 세션당 한 번만 구하기**: 호출은 줄지만 오차를 앱 전역 상태로 들고 있어야 하고, 세션 중에 기기 시각을 바꾸면 바로잡히지 않는다. 화면을 열 때마다 호출해도 무료 한도를 크게 밑돌아 비용 차이가 없다.
- **앱 시작 때 서버 시각 구하기**: 초대 코드 화면을 열지 않는 스태프·뷰어까지 매번 호출하게 되고, 로그인 전에는 호출할 수 없다.

## Consequences

- `issueInviteCode`가 배포되지 않은 상태에서 앱이 호출하면 Android·iOS에서 `not-found`가 와 "점포를 찾을 수 없다"로 보인다. Functions를 Rules보다 먼저 배포한다(CLAUDE.md의 배포 순서).
- 발급에 Functions cold start가 더해진다. 관리자가 가끔 하는 동작이라 감수한다.
- 만료 상수(15분)는 앱이 표시와 공유 문구에 계속 쓰므로 앱과 Functions 양쪽에 남고 계약 테스트로 묶는다.
